## Ledger rule
Production has no migration ledger. Repo migrations 20261010..12 describe the manual baseline. They are
recorded as applied **only** in a database where `bootstrap.sh baseline` just applied them (staging), or,
later, in production only after a separately authorized decision. Nothing here creates production records.

## Staging procedure
1. Founder creates `tripp-staging` (free tier), sets its DB password, enables nothing else.
2. GitHub → Settings → Environments → `staging` (required reviewer: founder) with secrets
   `STAGING_DB_URL` (session pooler URI containing the staging ref) and `STAGING_PROJECT_REF`.
3. Populate `00_org_membership.sql` from production Q1 (Hark, after the founder supplies the sections).
4. Actions → D04 Staging Bootstrap: run `baseline`, then `repair`, then `push`.
5. Staging Vault secrets, function deploy and function secrets per `docs/D04-B2.8-staging-runbook.md`, with
   `TRIPP_ENABLE_DOCUMENT_UPLOADS=false` until smoke tests pass.

## Rollback (staging, and the template for production)
1. Set `TRIPP_ENABLE_DOCUMENT_UPLOADS=false`; wait until no document is pending/processing (expiry runs every 5 min).
2. Run `supabase/staging/rollback_d04c.sql`.
3. `supabase migration repair --status reverted 20261012900000 … 20261023000000` (truthful after step 2).
4. Re-apply later with `bootstrap.sh push`; preflight re-checks and existing READY evidence is preserved.
Rehearsed in CI (R1–R9).
