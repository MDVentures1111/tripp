# D04-B2.7 — Final security audit and controlled deployment decision
Date: 2026-10-12
Scope: GitHub review branch only. No Supabase migration, function deployment, or live test was performed.

## Decision: NO-GO for production; CONDITIONAL GO for isolated staging
The private bucket and metadata schema are reported as previously deployed; B2.5/B2.6 migrations and Edge Functions remain review-only. Do not enable either feature flag.

## Critical findings
**C1 — Signed upload compatibility is unknown.** Verify that a signed token issued by service role can upload to quarantine with the restrictive storage.objects policy intact. Do not relax browser Storage RLS merely to make the transport work. Verify replay, overwrite, MIME/size behavior, expiration, and path binding against real Storage.

**C2 — Cross-service lease fencing is not atomic.** A lease check precedes a separate Storage upload. If the lease expires in between, a stale worker may still create the final source. The final source is created with upsert:false, but competing workers can cause inconsistent attribution or failed promotion. No guarantee of exactly-once publication has been established.

**C3 — DOCX validator is structural only.** Central directory and names are checked but ZIP local/central consistency, OOXML relationships, CRC, decompression safety, malicious XML and malware scanning are not fully verified. Do not describe accepted files as safe.

**C4 — PDF validator is signature/trailer only.** It is not a PDF parser, sanitizer, or malware scanner. Do not process untrusted documents in privileged downstream parsers without sandboxing.

**C5 — Stale-source reconciliation assumes validated source.** It rechecks basic structural validity and metadata size, but cannot cryptographically prove source matches the bytes previously validated before promotion. Consider persisting SHA-256 and a verified provenance record, or move finalization into an isolated single-writer service.

**C6 — Worker is not scheduled.** Maintenance endpoint requires TRIPP_RECONCILER_SECRET and TRIPP_ENABLE_RECONCILER=verified; neither is a substitute for scheduling, alerting, or monitoring.

## High findings
- H1: Supabase migration history is not reconciled. Manual SQL execution must be schema-reviewed and recorded before automated deployment.
- H2: Endpoints have no documented operational rate limits or quotas; a malicious authenticated user could create many pending records.
- H3: Reconciler processes up to 25 objects per run and can download up to 20 MiB each; verify memory, wall-clock budget, and partial progress.
- H4: API error responses are generic; structured server-only audit logs/metrics and alarms are absent.
- H5: Signed upload token expiration (reported 7200 seconds) must be confirmed against the actual Supabase runtime.
- H6: DOCX and PDF test fixtures include no real-world valid DOCX; no CI or runtime execution evidence exists.
- H7: CORS restrictions alone do not authorize non-browser callers; server JWT and role checks are the actual controls.

## Required isolated-staging sequence
1. Create separate Supabase staging project and bucket. Do not point staging tests at production data.
2. Reconcile schema and apply A1/A2/B2.5/B2.6 in correct order after inspecting each SQL file. Check function grants and storage RLS.
3. Deploy read-only list/download endpoints and test nonmember/viewer/mismatched-deal cases.
4. Deploy initiate/finalize with upload issuance disabled; assert 503 when flag unset.
5. In staging only, enable upload issuance temporarily and test signed token on quarantine, source-path denial, overwrite/replay denial, 20 MiB behavior, malformed content, and signed-token expiry.
6. Execute concurrent finalizer tests and force failures before/after source upload; verify no unvalidated source becomes READY.
7. Deploy reconciler disabled; test secret rejection, then enable staging-only with a dedicated scheduler after reviewing retention and monitoring.
8. Record test output, timestamps, commit SHA, bucket policies and rollback evidence.
9. Hold production approval until C1–C5 are addressed with testable evidence.

## Rollback
Keep production flags unset. On staging failure, disable both flags and scheduler first, then stop function traffic. Do not delete final source objects or overwrite metadata to mask inconsistent states. Preserve logs and reconcile each pending/processing record.

## Current outcome
**Security audit complete at static-review level only. Deployment preparation documented. Live transport verification and release authorization are NOT complete.**
