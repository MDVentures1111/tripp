# D04-B2.5 — Recovery and reliability verification

## Implementation committed
- Database migration adds `processing`, a claim token, and a 10-minute lease.
- Service-role-only RPC atomically claims a pending document.
- Completion RPC verifies matching token, processing state and live lease.
- Finalize endpoint claims before accessing quarantine and completes via RPC.
- Existing final object uses `upsert:false`.

## Critical release blockers
1. **Reconciliation worker missing.** A failed process can leave `processing` after lease expiry. Do not automatically mark it failed if a final source exists; inspect the source, verify bytes and metadata, and then reconcile under an exclusive claim.
2. **Crash consistency.** Object promotion and Postgres READY transition are not a distributed transaction. Implement a deterministic reconciler for `processing` and orphaned objects.
3. **Lease expiry.** A slow finalizer could continue promoting after its lease expires. Recheck ownership immediately before promotion or use a fenced storage-promotion mechanism; add concurrent/timeout tests.
4. **Cleanup.** Pending rows older than signed-upload validity and quarantine objects must be swept, but only after checking active leases and the final source.
5. **Error path.** If an exception occurs after claiming, the row remains `processing` until reconciliation; this is intentional fail-closed behavior, not a complete recovery mechanism.
6. **Upload issuance is disabled by default.** Keep `TRIPP_ENABLE_DOCUMENT_UPLOADS` unset.
7. **Live testing absent.** Test RPC grants, concurrent claims, lease expiry, crash at each stage, and signed upload restrictions in a non-production project.
8. **Document content validation** remains preliminary; OOXML structural checks are not malware scanning.

## Required runtime matrix
- 2 simultaneous claims for same document -> exactly 1 succeeds.
- Wrong token cannot complete; expired token cannot complete.
- Viewer/nonmember cannot finalize.
- Failure before quarantine read, during validation, after promotion, and after READY all recover deterministically.
- Old quarantine credential cannot mutate final source.
- No source object is deleted without proving its owning document and state.
- Source and metadata remain organization/deal/document scoped.
- Cleanup preserves active uploads and never makes an unvalidated object downloadable.

## Deployment order
Review migration against live database -> deploy to isolated Supabase test project ->
execute negative/concurrency tests -> implement reconciler and cleanup -> verify
private bucket policy -> enable uploads only after full approval.
